# SUMH 场景化使用指南

本页把已有的模块规则、用户隐藏、Maps、Kernel Build 和 `su` 路径能力组合成可操作的流程。基础内容按 2026-10-16 源码核对，后续批次与场景已补至 2026-10-19；命令示例没有在实际设备上执行，不代表设备验证通过。功能增强、接口草案和后续内核扩展见[全面改进计划](../../plans/SUMH-comprehensive-improvement-plan-2026-10-16.md)。

本页代码块中的命令均为现有入口；第八批已实现 `sumh maps preview`，第九批增加只读 `module plan/explain` 和五类 Manager 草稿模板，详见[模块规则指南](sumh-module-rules.md#只读计划预览与路径解释)。第十批已实现单模块 inspect、normalize dry-run 与额外分区发现/条件保存，第十一、十二批增加操作查询与预登记执行，第十三至十五批增加用户隐藏定义、分组启停和按 ID 恢复资源结果，第十六批增加完整/选中定义文件导出、导入预检与分组提交，见[定义指南](sumh-user-hide-definitions.md)。第二十六批增加未启用 `profile` 方案存储和资源差异；`module apply`、`profile activate` 和运行恢复尚未实现，不能用作当前操作步骤。

补充流程：使用模块模板前，先记录原有完整 mode/rules；在模块设置打开模板、填写路径、审查相对当前草稿的差异，再明确替换草稿。模板不自动保存或做设备预检。需要比较保存配置与候选规划时，使用上述指南的 JSON 和精确 CLI；预览仅观察当前可挂载模块，发生 stale/unknown 时先排查并重新读取。取消/关闭仍保留模板输入和主草稿；保存前撤销需手动恢复记录的完整 mode/rules，当前没有通用的一键整份草稿重置。已保存则恢复原完整定义并重启，不使用全局 clear。

## 使用前确认

命令在已授权的设备 root shell 中运行，使用 `/data/adb/ksud` 完整路径。`example.module`、`/vendor/etc/example` 等名称是占位符，需替换为自己的测试模块和路径。模块用例先在不涉及系统启动必需文件的合成模块中验证。

下面的查询分派本身不修改配置，但当前首次查询可能拉起未运行的 daemon，而 daemon 启动包含已保存规则的恢复路径。需要严格无变更采集时，在专用测试环境中确认控制器已经运行并完成启动恢复，再执行查询。首批 R01 已统一安全模式等自动恢复条件，主机回归通过、设备验收待完成；正常模式下仍不能把查询命令称为端到端绝无副作用，见[实施账本](../../plans/SUMH-implementation-progress-2026-10-16.md)。

```sh
/data/adb/ksud sumhp api meta
/data/adb/ksud sumhp api backends
/data/adb/ksud sumhp config show
/data/adb/ksud sumhp module list --all
```

保留当前模块的模式与完整规则列表，以及这次要修改的配置字段。`module configure` 一次替换该模块的**完整**路径规则，空数组会清空该模块的路径规则，不能当作追加操作。`module list --all` 是检查输出，不是可以直接导入的备份格式。

保存、应用和观察是三个步骤：保存定义不保证当前内核已应用；规则已注册也不保证所测试进程处于该规则的作用范围。验证时记录应用 UID、是否获得 root 授权、是否卸载模块，以及观察对象所在的命名空间。root 看到文件或真实挂载信息，不能据此断定普通应用中的规则失败。

在管理器编辑 Kernel Build 或挂载来源、临时目录、镜像路径时，外部配置刷新会自动更新未编辑字段；有未保存输入的字段保留草稿，并提供使用最新保存值或保留草稿的选择。决策只影响对应字段，不会自动提交。路径校验失败或保存尚未确认时，编辑器保持打开；较早保存的读回不会覆盖之后的新输入。原值/日期辅助按钮与这些决策同样只修改草稿。

| 能力 | 选择与验证的重点 |
| --- | --- |
| 模块文件视图 | 需要模块本次启动实际归属 SUMH；应用是否获得模块视图还受现有应用策略控制。 |
| 用户隐藏 | root 和已授权应用具有豁免；存储服务另有与存储目录相关的范围处理。 |
| Maps / 挂载信息 | 分别受各自开关及观察者策略控制，不能照搬模块文件视图的判断。 |
| Kernel Build | 修改初始 UTS 命名空间的字符串，影响范围不按应用 UID 划分。 |
| 自定义 `su` 路径 | 改变既有 sucompat 的路径入口，沿用授权策略，不新增 root 授权。 |

基础约束见[模块路径规则](sumh-module-rules.md)、[Maps 路径规则](sumh-maps-rules.md)、[Kernel Build](sumh-kernel-build.md) 和[验证指南](sumh-validation.md)。

## 1. 仅使用模块中的少数文件

**目的与条件：** 模块带有一整套内容，但只想使用其中一个文件。模块必须实际使用 SUMH；Auto 当前不会自动选择 SUMH，非 Auto 的全局后端设置也可能覆盖模块选择。

**入口与步骤：** 管理器模块挂载设置或 `module configure`。先记录原规则，再将根路径设为 `none`，将需要的文件设为 `sumh`：

```sh
/data/adb/ksud sumhp module configure example.module sumh \
  '[{"path":"/","mode":"none"},{"path":"/vendor/etc/example.conf","mode":"sumh"}]'
/data/adb/ksud sumhp module list --all
```

按当前管理器流程重启生效；`config apply` 不保证重新编译已生效的模块映射。选中文件必须真实存在于模块相应的分区目录中，路径规则不会生成文件内容。

**期望观察：** 选中文件来自该模块，其他模块文件被跳过；被跳过的路径仍可能由系统或其他模块提供，`none` 不代表删除文件。

**失败处理：** 依次检查全局后端、模块实际策略、文件的分区布局、路径别名和应用策略；不要用反复清空全部规则来排查。

**撤销：** 恢复此前记录的模块模式和完整规则并重启。仅在原来没有路径规则时，才用空数组恢复该状态。

## 2. 排除目录，但保留其中一个子项

**目的与条件：** 使用模块大部分内容，跳过一个目录，同时保留目录中的个别文件；适用条件与场景 1 相同。

**入口与步骤：** 将父目录设置为 `none`，为需要保留的子项增加更长的 `sumh` 路径：

```sh
/data/adb/ksud sumhp module configure example.module sumh \
  '[{"path":"/vendor/etc/example","mode":"none"},{"path":"/vendor/etc/example/keep.conf","mode":"sumh"}]'
```

保存完整列表并重启；修改现有模块时需要把原来仍需保留的规则也包含在列表中。

**期望观察：** 普通映射按最长路径前缀匹配，`keep.conf` 使用模块文件，目录内其余模块项被跳过。**不要把父目录改成 `hide` 来实现排除：** 父目录隐藏后，子项映射不能重新打开它。

**失败处理：** 检查 `/system/vendor` 与 `/vendor` 等路径是否解析为同一目标，以及是否存在不同模式的别名冲突。保留原始路径定义，由现有 Planner 解析，不手动批量替换路径字符串。

**撤销：** 恢复原完整规则；如果仅追加过这两条且确认没有覆盖原定义，也可逐条 `module remove-rule` 后重启。

## 3. 合并资源目录并保留系统兄弟项

**目的与条件：** 为现有目录增加或覆盖少量资源，同时保留未被模块覆盖的系统项。模块实际后端为 SUMH，目标目录已经存在，源分区目录为真实目录。

**入口与步骤：** 在模块的标准分区树放置文件，设置模块为 SUMH，保存后重启。普通用户不需要直接调用 MERGE ioctl；控制器根据目录结构和路径规则选择整目录合并或逐项映射。

**期望观察：** 合并目录同时包含原有兄弟项和模块项，同名目录项只显示一次。嵌套路径例外、whiteout、符号链接、路径别名或过深目录可能使编译器选择逐项处理。字符设备 `0:0` 或带对应 whiteout 属性的空文件按隐藏条目处理；`.replace` 和 opaque 目录替换仍可能被拒绝。多个模块同名内容的结果不能仅凭目录去重推断。

第二十一批的通用 MERGE 收集器使用同一份名称集合执行注入和去重，覆盖五个以上来源的动态重复名，不依赖目标子项已经进入 dcache。它按每次读取重新收集，不能保证修改来源后继续使用旧目录游标仍得到固定顺序。单次容量、错误码及暂不支持的目标见[目录读取边界](sumh-module-rules.md#长路径和目录读取失败)；真实设备和并发验收尚未完成。

第二十七批进一步让 MERGE 规则持有完整挂载/目录引用，后续收集不再用源字符串自动换到替代目录。目录内容仍可变化，递归子项仍独立解析；替换源根后需要按受支持阶段重新规划，不能用重复登记当刷新。注册时的查找能力缺失、锁竞争及部分发布处理见[源对象身份与更新边界](sumh-module-rules.md#源对象身份与更新边界)。

**失败处理：** 查看控制器日志中的不支持元数据、别名冲突、扫描及 ioctl 错误。编译阶段失败会发生在清理旧映射前；安装阶段失败仍可能留下部分完成的结果。不要为了让预检通过而删除原模块的 `.replace` 或 opaque 标记，这会改变模块语义。

读取时遇到 E2BIG、ENOMEM 或来源访问错误，应记录具体目录和错误，检查容量、内存或来源是否仍可访问。通用收集器在输出前报告这些失败，不把不完整列表当作成功；无需反复清空或重建全局规则。EAGAIN 的分类锁竞争可在原因消除后重新读取，EOPNOTSUPP 需调整受支持的来源或等待对应能力实现。

**撤销：** 恢复原模块内容、模式和规则并重启。需要停用本次启动的整个模块时使用场景 4；不要在仍被使用的源目录上直接批量移动文件。

## 4. 本次启动暂时停用和恢复模块

**目的与条件：** 排查本次启动中某个模块的影响。模块必须在**本次启动**已经归属 SUMH；仅把保存模式改成 SUMH 不能取得热操作资格。

**入口与步骤：** 查看模块列表及后端状态后执行：

```sh
/data/adb/ksud sumhp module hot-unmount example.module
/data/adb/ksud sumhp module list --all
# 完成对比后恢复本次启动的选择
/data/adb/ksud sumhp module hot-mount example.module
```

**期望观察：** 命令修改本次启动的选择，并重放 SUMH 模块映射，可能影响整个 SUMH 运行集合。它不是 OverlayFS/Magic Mount 的热切换入口，也不是永久禁用模块。已经打开的 FD 或已建立的 mmap 不保证立刻切换到新内容。

**失败处理：** 若提示本次启动未归属 SUMH，保存配置后重启；若部分完成或结果未知，先读取 `module rebuild-status`，再分别检查模块映射与 Maps 恢复。第二十四批起同启动未解决的记录阻止再次重建，不能删除记录或全局 clear 解锁；热选择只在确认内核尚未修改时恢复。详见[重建记录指南](sumh-module-rebuild.md)。外部 owner 场景按控制器限制处理。

**撤销：** 恢复操作前选择：原先挂载则执行 `hot-mount`，原先暂停则执行 `hot-unmount`，然后重新验证实际视图。需要改变下次启动行为时使用现有模块挂载设置并重启，不依赖本次启动标记。

## 5. 预先登记稍后才出现的隐藏路径

**目的与条件：** 路径由应用或挂载流程稍后创建，希望保留定义并在条件具备后绑定。建议使用支持受管隐藏所有权与状态查询的内核；旧式 HIDE 兼容路径不能提供相同的管理保证。

**入口与步骤：** 管理器“隐藏路径”支持添加、搜索、筛选、多选、批量处理和失败重试。也可保存一条测试定义：

```sh
/data/adb/ksud sumhp hide add /data/local/tmp/sumh-scenario-future/item
/data/adb/ksud sumhp hide list
```

在管理器查看该定义的等待绑定、绑定中、已绑定或错误状态；让测试程序正常创建目标及父目录，再查看状态和实际访问结果。`hide list` 只列保存路径，不能替代管理器中的绑定状态。

**期望观察：** 内核对已注册的受管定义进行事件驱动重试；目标出现后需观察绑定结果，并由处于隐藏作用范围的进程验证。`SUSPENDED` 表示全局 SUMH 停用，当前不是用户可写的逐条暂停状态。

**失败处理：** 检查父目录、路径解析、内核可用性和管理器错误；通过已有单项或批量重试入口恢复。`hide apply` 用于同步已保存集合；第十三批起也可按稳定定义 ID 定向重试，须先取得当前 revision，并使用[定义状态与条件 CLI](sumh-user-hide-definitions.md#先读取状态和版本)。停用项不会因重试重新启用，未知操作结果先查询。不要将“已保存”当作绑定成功。

**撤销：** 在管理器删除该用户定义，或执行 `hide remove` 后读回并验证。受管入口按用户所有权移除；旧内核的兼容删除没有相同隔离保证，不要用它处理与模块 HIDE 重叠的路径。

### 大量路径的草稿与文件分批导入

当前 Manager 的用户隐藏页会把新增、批量和逐规则草稿保存在本机应用私有目录；取消编辑保留草稿，成功提交后移除已完成输入。批量失败路径也保存，可继续重试。草稿不属于已经启用的隐藏定义，重置草稿不会撤销内核规则。

从用户隐藏页的“更多 → 导入”打开编辑器。文本可直接粘贴，每批最多 1024 行、256 KiB；每条路径最多 4095 个 UTF-8 字节。所有用户隐藏草稿合计 1 MiB，预算包含重试所需空间。超限会拒绝本次修改并保留原草稿，不截断路径；先完成或重置其他草稿，或改用文件分批输入。

导入较大 UTF-8 文本文件时，先完成或清空当前批量草稿，选择“分批导入 UTF-8 文件”。每次读取最多 256 行、64 KiB，检查预览后添加有效项，再读取下一批。文件中的换行分隔路径，末尾空格保留；行过长或编码错误会显示具体错误，修改文件后重新选择。含 LF/CR 的单个路径应使用单条编辑，不能通过逐行文件表达。

当前批次会作为草稿保存，文件余下部分不持久保存。离开页面或重启应用后需重新选择文件；已保存路径通过预览去重。页面显示“正在保存”时尚未确认写入；保存失败输入仍留在内存，请重试。无法读取已存草稿时暂停编辑，避免覆盖未知内容。应用卸载/清除数据会删除这些本机草稿；草稿并非跨设备备份。

本轮宿主测试验证存储和预算，设备旋转、进程终止及 TalkBack 的完整验收仍见[实施记录](../../plans/validation/SUMH-batch-03-validation-2026-10-16.md)。

## 6. 文件替换后重新解析 Maps 路径规则

**目的与条件：** 路径规则仍指向同一个名字，但目标或替换文件被更新、原子替换或重新挂载。需要内核支持 `managed_maps`，目标和替换路径都能在 init 挂载命名空间解析为普通文件。

**入口与步骤：** 在 Maps 设置查看保存定义及开关，或执行：

```sh
/data/adb/ksud sumhp sumh maps list-paths
/data/adb/ksud sumhp sumh maps preview
/data/adb/ksud sumhp sumh maps apply
```

创建路径规则、长度限制及开关设置的完整步骤见[Maps 路径规则](sumh-maps-rules.md)。应用前先确认替换文件也已经就绪；默认没有持续监视文件替换的功能。

**期望观察：** `apply` 重新读取当前 inode/device，整批替换受管规则，并遵循保存的 Maps 开关。原地写入一般保留文件身份，原子替换或重新挂载可能改变身份；已有映射可继续持有旧文件对象，不能只按路径字符串判断。Maps 仅调整策略范围内的 maps/smaps 文本，不重定向文件读取，也不修改文件内容或访问权限。

**失败处理：** 任一路径缺失、类型错误或多个目标解析到同一身份会使整批规则替换失败，保留旧受管集合。修复后重新应用。规则替换和开关设置为不同请求，后一步失败不保证前一步未发生。匹配时精确 device 优先于 device=0 通配；同一匹配键下临时数字规则优先于受管规则，也需纳入排查。

管理器中，同目标保存的较早读回会保留之后修改的草稿；只有仍与提交内容相同的草稿才自动收起。添加或重命名与后续编辑交错时，当前定义尚无稳定身份，可能出现重复目标或原目标已移除的提示：保留输入，先核对已保存列表，再明确选择要编辑的定义；不要用全局清理绕过冲突。

若返回 `outcome_unknown` 或 `partial`，可能已经提交但确认消息丢失或确认记录写入失败，不能当作旧集合仍在或自动重放。先执行精确 `sumh maps preview`：该入口不启动 daemon 或恢复，区分本次解析与实际提交历史。同启动 pending 会阻止自动恢复；明确发起新的 apply 后会关联被取代的 pending ID。旧 ABI 无法核实完整运行集合时仍保留未知。

**批量复用：** 在 Manager 选中已保存定义并复制导出 JSON；导入文件或粘贴文本后，选择合并/替换并审查差异，同目标冲突需明确处理。点击保存并应用前只有草稿。只交换路径，不导出运行 inode 或临时数字规则；失败保留输入。格式、预算与恢复旧定义的方法见[Maps 指南](sumh-maps-rules.md)。

**撤销：** 删除本场景新增的目标定义，或恢复原替换路径，再明确应用。删除后剩余路径解析失败时，旧集合仍可能保留；应修复错误并再次应用。`maps clear` 会清空所有当前 Maps 规则，不能作为单条规则的撤销方式。

## 7. 理解映射写入的实际落点

**目的与条件：** 开发模块时确认编辑、创建和 rename 会修改哪个对象。只使用专用的合成模块、可丢弃文件和原始内容副本；使用有访问权限且确实获得模块视图的测试进程。

**入口与步骤：** 在测试模块中准备单文件映射及有源目录映射，按正常 SUMH 流程加载；分别记录可见路径与源文件的内容及身份。依次做一次原地编辑、一次临时文件替换、一次目录内新建或 rename，每一步后重新打开路径并比较源内容。另保留一个操作前已打开的 FD，用来区别已有句柄和新打开的结果。

**期望观察：** 当前部分 vnode 操作会委托给固定的源对象，写入可能直接修改模块源文件；“虚拟映射”不等于副本或只读。无源的虚拟目录不提供同样的写透行为，可能返回只读错误；跨源或不满足约束的 rename 也可能拒绝。原地修改、替换 inode、旧 FD 和新 open 的结果需分别记录。

第二十八批普通非链接源改为一次捕获，MERGE 物化从持有的父目录解析非链接子项；在专用合成目录中另测“源根被 rename/替换”与“同一源根内子项被替换”，两者不可混为一谈。前者不应仅因描述字符串改变而切换已持有根，后者可能被随后子项查找观察到。第三十一批链接跟随后检查会拒绝仍可观察的叶对象替换；在测试中分别记录持续替换、A→B→A、动态链接和检查后变化，不能把后一类通过当成原子性证明。符号链接配对、目录内容和控制器路径计划都不是原子快照，具体[身份与容量边界](sumh-module-rules.md#源对象身份与更新边界)应纳入期望记录。遇到错误先查询重建记录，确认影响范围，再按支持的阶段重新规划，不循环重试。

**失败处理：** 保留操作、errno、可见路径和源路径，区分权限拒绝、只读容器、跨设备边界和映射过期。不要通过提高全局权限或改写生产文件来绕过合成用例的错误。

**撤销：** 先停止测试程序、关闭测试 FD 并停用测试模块，再恢复源文件副本；重新加载或重启后验证。只撤销映射不会恢复已经写入源文件的数据。

## 8. 内核构建字符串的兼容性实验

**目的与条件：** 测试自己的软件如何处理不同 Release/Version 字符串。需要 `kernel_build_spoof` 能力，且应保存当前设置及原值。

**入口与步骤：** 管理器 Kernel Build 卡片或现有 CLI。以下仅替换 Version，Release 使用原值：

```sh
/data/adb/ksud sumhp sumh kernel-build show
/data/adb/ksud sumhp sumh kernel-build set default \
  '#1 SMP PREEMPT Fri Aug 23 03:08:10 UTC 2024'
uname -r
uname -v
```

`show` 已返回原值和 `suggested_version` / `suggestion_source`。建议值来自 ROM 的 `ro.build.date`，不是内核真实编译日期。首批 F10 已接通管理器的“使用原始 Release”“使用原始 Version”和“使用系统构建日期”：分别只填对应草稿，核对原值、当前值和待保存值后再显式保存；读取失败或建议不可用时对应按钮禁用，刷新运行值保留草稿。原始 Release 推断的 KMI 标签不能代替 ABI 探测。单字段编辑、64 字节 UTF-8 限制和恢复阶段详见[Kernel Build](sumh-kernel-build.md)。

**期望观察：** 初始 UTS 命名空间中的字符串改变，真实内核代码、ABI 和 KMI 不变；既有独立 UTS 命名空间不会同步更新，启用期间新建的命名空间还可能保留当时的副本。手动设置立即应用，保存的启动阶段只决定后续开机恢复时机。

**失败处理：** 分开检查查询、保存和内核应用错误。到达应用阶段后，`set/reset` 返回 `saved`、`applied`、`runtime_result` 和 `detail`；`enabled` 是请求方向，不是实际状态证据。`set` 保存后应用失败不会盲目写回旧配置，因此新意图仍可能在后续恢复时生效。遇到 `outcome_unknown` 先查询，不自动重试；`rolled_back` 也只表示运行值的恢复，不能代替检查保存定义。原值读取失败时不要把当前替换后的 Release 当成原始 KMI 的可靠依据；字符串实验不能验证设备是否支持某个 KMI。

**撤销：** 使用 `/data/adb/ksud sumhp sumh kernel-build reset` 尝试恢复原值并关闭持久化；检查两个阶段的结果，再执行 `show` 及读取验证。能力不可用时可能只保存停用意图而未执行运行恢复。若操作前已有自定义设置，需要恢复之前的自定义字段和阶段，而不是将 reset 当作原设置恢复。已有独立 UTS 副本还需结束相关测试进程后重新验证。

## 9. 自定义 `su` 路径

**目的与条件：** 为自己的授权工具设置明确的 `su` 入口路径。设备需支持 su-path 配置；父目录必须能解析，目标不能与已有文件冲突，仍沿用既有 root 授权策略。

**入口与步骤：** 管理器已有的 `su` 路径设置或 `ksud su-path`，不是 `sumhp` 子命令：

```sh
/data/adb/ksud su-path get
# 仅在确认 /system/bin 父目录可用且目标名称未被占用后使用
/data/adb/ksud su-path set /system/bin/example-su
/data/adb/ksud su-path get
```

使用已授权的自有测试工具，通过返回的完整路径调用入口；不要依赖原 PATH 或缓存的旧路径。路径必须为规范绝对路径，不含空段、`.`、`..` 或控制字符。

**期望观察：** 当前配置和后续启动恢复的路径改变；未授权应用不会因此取得 root。查询路径或目录可见性不能替代实际授权调用验证。

**失败处理：** 区分目标已存在、父目录不可用、路径非法、权限、能力不支持、忙和持久化失败。持久化错误可能发生在运行时已改变之后，因此应读回当前路径，不能假定所有失败都无变化。

**撤销：** 原来使用默认路径时执行 `/data/adb/ksud su-path reset`；原来已有自定义路径时使用 `set` 恢复记录值。随后读回，并让测试工具重新解析入口。

## 10. 联合排查后端回退与路径冲突

当前仓库还提供 `ksud sumhp api runtime`，可区分六项功能的内核开关、可用性、活动状态和读取错误。该 JSON 包含 boot ID 与控制序列，不包含完整配置 revision，也不证明普通应用的实际视图。具体字段、旧内核兼容和条件写入限制见[运行状态查询](sumh-runtime-state.md)。

第六批可用 `ksud sumhp api inventory` 查询结构化枚举能力，并用 `api inventory mapping`、`merge`、`maps_managed` 等逐类分页核对登记记录。保持同一 instance/generation，连续读取至末页；未知、过期和旧文本回退不能解释为完整空集合。路径编码可无损表达换行和非 UTF-8 字节；来源路径不能证明模块 owner。Manager 的保存／运行状态面板同时展示控制面差异和最后操作，具体用法及完整性边界见上述指南。

**目的与条件：** 模块保存为 SUMH，但实际视图不符合预期，或多个模块提供同名内容。先收集当前状态，避免主动重放；同时按“使用前确认”检查控制器是否已经运行，首次拉起 daemon 的恢复行为也要记录。

**入口与步骤：** 使用现有查询命令及管理器日志：

```sh
/data/adb/ksud sumhp api meta
/data/adb/ksud sumhp api backends
/data/adb/ksud sumhp module list --all
/data/adb/ksud sumhp module check-conflicts
/data/adb/ksud sumhp sumh list
/data/adb/ksud sumhp recovery status
```

按全局设置、模块保存模式、本次启动归属、源目录布局、路径规则和实际观察者依次比对，并保存控制器相关错误。明确检查是否存在外部 MetaModule owner。

**期望观察：** 保存模式与当前后端可能不同；不支持的布局、能力或启动保护都可能影响选择。`check-conflicts` 是模块文件树的同路径扫描，不计算所有别名、最长前缀、父目录隐藏或跨后端最终胜出关系；空结果不等于没有语义冲突。内核规则列表也可能被截断，不能把未显示的条目解释为不存在。

**失败处理：** 查询失败时保留错误和原配置，恢复控制器连接或内核能力后重试。当前 `config sync-partitions` 仅打印扫描到的候选，即使输出含 `Added` 也没有保存分区配置；不要以此判断额外分区已经生效。`module normalize` 当前会修改布局，没有已实现的 `--dry-run`，不能当只读诊断使用。

**撤销：** 控制器已运行时，上述查询分派本身无需撤销；首次拉起 daemon 若触发恢复，须核对实际恢复结果，不能假定运行规则未变。如果随后进行了试验性配置修改，恢复记录值并重启；不要用 `mount-all` 强制重建已完成启动后的 OverlayFS/Magic Mount。

## 11. 更换内核后维护保存配置

**目的与条件：** 升级、降级或切换到能力不同的内核，同时保留有效的模块和路径定义。

**入口与步骤：** 重启后先查询 `api meta`、`api features` 和 `api sumh`，再查看模块、隐藏和 Maps 的保存列表。把每项情况区分为支持、明确不支持、关闭、读取失败或已保存待应用；读取错误不等于不支持。

**期望观察：** 配置仍可用于恢复或后续兼容内核；当前不具备能力的设置不应被当作已经生效。模块后端可能改变，旧式隐藏兼容路径与受管所有权入口也不具备完全相同的管理语义。

**失败处理：** 优先处理控制器与内核协议/能力不匹配，保留原定义和原始错误。未来格式、整体 JSON 损坏或字段问题都不应通过覆盖为空配置“修复”。不要仅因当前查询失败，批量删除隐藏或 Maps 定义；相关完整的状态保护仍是改进计划的验收项。

**撤销：** 恢复兼容的内核与配套控制器后，先查询再按对应入口重新应用。降级涉及模块对象格式等持久化差异时，使用事先保存的旧格式备份或明确的转换，不把新版保存文件直接当作旧版可读配置。

## 12. 按归属清理和撤销

**目的与条件：** 只撤销这次试验的修改，避免影响其他模块、用户定义或临时规则。先对照试验前记录，确认删除对象的归属。

**入口与步骤：** 按资源类型选择操作；涉及保存与运行状态的操作后都要读回，再由相应观察者验证。

| 要撤销的对象 | 当前操作 | 期望结果与失败处理 |
| --- | --- | --- |
| 用户受管隐藏 | 管理器删除或 `sumhp hide remove <path>` | 删除保存定义并尝试移除用户受管内核记录；保存成功、内核失败时需继续核对，旧内核兼容路径不保证所有权隔离。 |
| 模块路径规则 | `module remove-rule <id> <path>` 或恢复完整 `configure` | 保存规则变化后重启；若原规则被覆盖，需恢复原模式，而不是只删新规则。 |
| 本次启动的模块选择 | `module hot-mount` / `hot-unmount` | 恢复本次启动选择；受 SUMH 归属限制，可能重建整个 SUMH 集合。 |
| 受管 Maps 路径定义 | `sumh maps remove-path <target>`，或恢复原配置后 `sumh maps apply` | 只替换受管部分；剩余路径校验失败时旧运行集合可能保留，应修复后重试。 |
| 临时数字 Maps 规则 | 同键再次 `maps add` 可恢复事先记录的值 | 支持新接口时可用 `api inventory maps_temporary` 连续分页读取登记集合，步骤见[运行状态查询](sumh-runtime-state.md)。第二十九批已有携带 instance/generation 的精确 remove，第四十二批另提供可选预约与历史回执；见场景 25、32。分页 ID 不是删除句柄，不使用全局 clear 冒充单项撤销。 |
| Kernel Build | 恢复原自定义值，或原来关闭时 `kernel-build reset` | 分别核对持久设置、运行字符串及独立 UTS 副本。 |
| 自定义 `su` 路径 | `ksud su-path set <旧路径>` 或原来默认时 `reset` | 读回并通过已授权工具验证；恢复入口路径不会改变授权。 |

**失败处理：** `sumh clear` 会影响广泛的运行规则及功能状态；`sumh maps clear` 清空临时和受管 Maps 运行集合，但不会删除保存的路径定义，后续应用或恢复可能重新装入。两者都不能用作通用“修复全部”或单项撤销。`recovery reset` 仅重置启动保护记录，不恢复模块或配置；写入、同步、删除或读回失败时返回非零退出码和 `ok:false`。失败后先查询 `recovery status`：`counter_state` / `disable_marker_state` 区分缺失、有效、损坏和不可读，未知计数返回 `null`，存储异常时停止自动挂载。发生“已替换/删除但持久性未确认”的错误时，当前可见状态可能已改变，修复存储问题后可重试 reset，不能将该失败当作全部未执行。

**撤销清理：** 使用试验前记录重新添加对应定义并按原生效阶段恢复；保存配置不包含原始文件内容，不能恢复写透修改的数据。对未知或部分完成的操作先查询实际结果，再决定下一步。

## 13. 检查开发模块并预览布局调整

**目的：** 在安装前理解生产 Planner 会如何处理模块，以及 normalize 会移动或创建哪些路径。

**适用条件：** 授权 root、完整控制器私有目录、有普通 module.prop 的规范开发目录；这是单模块编译检查，不证明实际应用视图。

**入口与步骤：** 按[模块开发预检](sumh-module-rules.md#模块开发预检与规范化预览)依次运行 `module inspect <目录>` 和 `module normalize <目录> --dry-run`，阅读后端选择、动作/跳过理由和错误。保留开发目录备份，需要调整时再显式执行不带 dry-run 的 normalize，然后重新 inspect。

**期望观察：** 完整且稳定的只读结果，或明确的未知/过期/部分结果。实际 normalize 逐项展示已发生作用和持久性确认，不将失败简单解释成“没改动”。

**失败处理：** 冲突、变化或不支持 no-replace 时先检查现有布局；断连后重新 dry-run，不能盲目重放。平台别名问题与生产编译问题分别读取。

**撤销方式：** 只读阶段无需撤销。实际调整后使用事先备份恢复开发目录，或依据逐项结果人工核对恢复；程序没有持久逐项回滚协议，不使用全局 clear。

## 14. 为额外分区选择保存名单

**目的：** 让额外模块分区经过发现、选择和差异审查后进入下次启动配置。

**适用条件：** 当前发现完整/稳定，保存配置可读且版本受支持；新增项符合真实目标/别名/挂载事实检查。禁用模块也可提供候选来源，不代表其已挂载。

**入口与步骤：** Manager 设置→挂载→额外分区→发现→选择增删→预览→仅保存。脚本使用 `config discover-partitions` 与带本次 config_revision 的 `config set-partitions`，详见[分区步骤与限制](sumh-module-rules.md#额外分区发现选择仅保存)。保存是完整名单，先记录原值并保留不需要移除的旧名字。

**期望观察：** 只保存配置并提示重启；旧 sync-partitions 只返回候选 JSON。未知/不完整不会清空名单，保存后的 receipt 区分 saved、unchanged、partial 和 unknown。

**失败处理：** 并发配置变化时重新发现并审查；超时或读回失败保留草稿，不自动重发；新增资格丢失时修复来源或取消该新增项。

**撤销方式：** 用新发现的 revision 恢复原完整名单、保存并重启。当前挂载不会因仅保存立即恢复，已有未识别定义不会自动删除。

## 15. 命令断连后检查近期操作

**目的：** 查找已经登记的命令及其结果，避免把响应丢失误当成“没有执行”。

**适用条件：** 控制器支持 operation 查询（第十二批为 schema 2），调用者有 root 授权；命令走受记录执行链，且记录仍在 16 条/32 KiB 保留范围内。额外分区直接保存及部分自动恢复不在此范围。

**入口与步骤：** 新脚本优先按[预登记执行流程](sumh-runtime-state.md#提交前取得操作-id)用文件/stdin 的版本化 args 先 prepare，保存成功返回的 ID，再对同一输入 execute；原有 daemon 执行类命令需先明确 daemon 可用，该入口不启动或重试它；场景 32 的临时 Maps 追踪在本地执行，无需 daemon。断连后只对预先保存的 ID show/wait。对于普通旧 CLI，先运行 `ksud sumhp operation list`，按命令类型、boot ID 与现有记录确定候选；取得明确 ID 后运行 `operation show <id>`，需要短暂等候时运行 `operation wait <id> 5000`。必须使用精确本地命令，不通过 daemon call。字段与退出码见[近期操作历史与等待](sumh-runtime-state.md#近期操作历史与等待)。

**期望观察：** 未执行预约、已完成、失败或部分完成、未知结果分别显示。预约至多调用一次，缺失/淘汰 ID 不重建；参数摘要不固定配置、源文件或 Planner 版本。`command_completed` 仅表示命令返回成功，随后仍按资源核对保存配置、当前运行集合与实际观察者。

**失败处理：** 超时不会取消原命令；not_retained 不证明没有执行。同启动下多条同名命令可能无法唯一关联丢失的响应，不能直接选最新 ID 或自动重发。记录损坏/未来格式时保留文件并使用匹配控制器排查，不清空规则。旧启动的 started 仍为未知。

**撤销方式：** 查询无需撤销；未执行预约自然淘汰，不影响运行规则，当前不提供单条取消接口。需要撤销原变更时按第 12 节选择对应资源和事先记录的配置。操作历史不是配置恢复点，不包含源文件备份。

## 16. 按用途分组并暂停用户隐藏定义

**目的：** 临时关闭一组自己保存的隐藏路径，同时保留路径、名称和备注供下次使用。

**适用条件：** 配套第十四批 Manager/控制器、受管用户隐藏能力及 root 授权。可用 [Manager 定义工作流](sumh-user-hide-definitions.md#manager-定义工作流)或稳定定义 CLI；不把全局 SUSPENDED 当作逐条参数。

**入口与步骤：** Manager 用户隐藏列表点击条目编辑分组，选择精确组名后使用“停用整组”；确认列表包括被搜索隐藏的成员，版本变化必须重新审查。CLI 使用精确 `hide status` 分页读完定义并取得最新 revision；用 `hide annotate <id> <revision> <JSON>` 给选中项填写 group，每次修改后重新查询。需要暂停时执行 `hide disable-group <group> <revision>`。分组名按原始字符串匹配，命令参数需保留空格并正确引用。

**期望观察：** 定义仍存在且 enabled=false，对应用户受管注册消失，同路径模块 HIDE 保留。已停用定义不进入自动恢复的启用路径集合。注册成员关系与绑定/普通应用观察仍须分别验证。

**失败处理：** 版本冲突先刷新；保存成功但部分删除失败时保留配置，查询每条状态和操作记录后再选择重试。变更回包超过 64 项会标记不完整，必须查看全量统计和分页状态。无法读取或格式未知时保留原文件，不清空全局规则。

**撤销：** 以最新 revision 执行同组 enable-group，或只启用选定稳定 ID；恢复组名/备注用 annotate。删除定义使用 remove-id，重新创建会产生新 ID。旧 list/路径兼容工具仅返回启用路径，停用项使用默认定义列表或 status 管理。第十五批 Manager 定义操作预先保存 ID；超时后通过操作历史按原 ID 查询摘要和留存资源回执，不自动重发，不按最新同名记录强行关联。迁移备份与降级边界见定义指南。


## 17. 恢复隐藏修改丢失的回包

**目的：** 在 Manager 退出或回包丢失后，查清原操作结果并避免重复修改。

**适用条件：** 配套第十五批 Manager/控制器，操作走稳定定义预约流程，本地仍有 ID；精确资源回执还需服务端摘要与回执均在保留范围。兼容路径工具和其他资源没有本批保证。

**入口与步骤：** 用户隐藏→操作历史→核对 ID 和命令类型→查询结果。未结束时最多等待 5 秒再查。脚本使用 `operation show/wait/result` 的同一 ID；具体字段见[按 ID 恢复资源结果](sumh-runtime-state.md#按-id-恢复资源结果)。随后关闭历史、刷新完整规则列表，单独检查当前定义和注册。

**期望观察：** 原回包、命令摘要、留存资源回执分开显示；仅回执 observed 能提供当次资源详情，旧 boot 明确标记历史。恢复不清草稿、不自动继续未尝试的批量。

**失败处理：** not_retained/resource_unavailable 不证明未执行，未知不自动重发。损坏或未来格式不覆盖；保存错误时保留 ID 和错误记录，先检查当前状态再明确发起新操作。

**撤销：** “移除本地记录”仅删除本地关联。撤销目标修改使用当前 revision 的 enable/disable/annotate 等资源命令；查询历史不改变规则，不以全局 clear 清理。

## 18. 备份、迁移并合并完整隐藏定义

**目的：** 携带稳定 ID、原始路径、enabled、名称、备注和分组，在当前配置上审查后合并一份完整或选中的定义备份。

**适用条件：** 配套第十六批 Manager/控制器及相应交换能力。只读导出要求保存文件可读、格式受支持和版本一致，不依赖内核可用；提交要求受管用户隐藏能力、已知 boot ID、最新 revision 和运行中的 daemon。原路径文本复制/兼容导入不携带完整元数据，不能替代此格式。

**入口与步骤：** 用户隐藏默认定义列表→导入导出菜单→“导出全部定义”，或先多选再“导出所选”，保存为 JSON；文件选择器打开前会固定快照，不随之后的选择变化。目标侧先导出当前完整配置，再选“导入／预检定义”→选择 JSON 文件，或粘贴不超过 64 KiB 的文本→校验并保存本地草稿→“读取当前定义并预检”。核对全部字段、增加/修改/启用/停用数量及冲突：默认新定义停用，已有定义保持原 enabled；只有明确勾选“采用导入的启用状态”才按文件改变启停。保留已有定义、采用导入值、同路径保留本地 ID、同 ID 生成新 ID 或跳过均须按冲突类型明确选择；普通交叉冲突只可跳过。重新预检后“提交下一组”，每次最多 16 条实际变更，到达 30 秒后不再开始下一条。余项必须再次读取当前定义并预检，再明确提交，不自动续传。详见[完整定义文件交换](sumh-user-hide-definitions.md#完整定义文件交换)。

**期望观察：** 校验保存草稿不改变控制器或内核。实际提交逐条返回 operation ID 和保存/注册结果，第一条失败、部分完成或未知即停止。合并保留未导入的定义，不清空列表；已完成项重新预检后可成为无变更项。原始草稿、enabled 意图与冲突选择在成功或失败后都保留，重开窗口或进程重建后须重新预检。导出文件只保存六个定义字段，不包含运行身份、boot marker 或操作历史；注册成功仍不代表普通应用视图已验证。

**失败处理：** 文件最多 4 MiB + 256 字节、4096 条，规范编码后的持久配置最多 4 MiB；校验拒绝未知字段/格式、重复 ID/路径、非法 UTF-8 和容量溢出，不 trim 原始路径。旧文件回调与新草稿不符时保留新稿并报错。配置/boot 变化或无法完整读取时重新查询，不使用部分列表继续导入。提交超时后按原 ID 查询[资源结果](sumh-runtime-state.md#按-id-恢复资源结果)，再检查当前配置和注册；不因回执淘汰而重放。已送达命令不会因“停止”或 30 秒预算被撤销。导出失败的目标文件可能不完整，重新生成并检查结果。

**撤销：** 尚未提交时关闭窗口即可停止本轮操作，私有草稿继续保留。已应用时重新导入事先备份、明确审查并恢复所需字段；若需恢复原启停，明确采用备份 enabled。因为导入仅合并，本轮新增的定义必须另按已确认的稳定 ID 删除或停用，恢复备份不会自动删掉它们。不使用全局 clear，普通应用视图和重启状态仍单独验证。

脚本可用当前精确本地 `hide export` 输出整份定义，或 `hide definitions [revision cursor]` 分页读取；两者不启动 daemon、不迁移或查询内核。单条写入是 `hide import-id <id> <expected-revision> <JSON-fields>`，不是整份文件激活器。使用 JSON 序列化库构造[版本化文件/stdin 输入](sumh-runtime-state.md#提交前取得操作-id)，保留 prepare 返回的 ID 后再 execute；不拼接用户路径到 shell，不扩大 48 KiB/64 KiB IPC 限制。Manager/脚本预约执行不自动启动 daemon；直接公开 import-id 仍可能启动普通 daemon。源码、宿主检查与待设备验收范围见[第十六批验证](../../plans/SUMH-implementation-validation-batch16-2026-10-16.md)。

## 19. 保存前比较完整模块草稿并解释路径

**目的：** 检查当前模块草稿会如何改变生产 Planner 的编译贡献，并理解指定路径的匹配、别名、隐藏祖先和源文件写入落点。

**适用条件：** 配套第十七批 Manager/控制器及逐项预览能力；已有可读取的运行目录和 root 授权。当前可挂载模块集合是采样范围；disable/remove/skip_mount/本次启动暂停的模块可能不在其中。

**入口与步骤：** 模块设置中完成或取消单条编辑→“计划预览与路径解释”→手动读取保存配置→返回编辑器调整模式/完整规则或使用模板→重新打开并“比较当前完整草稿”。需解释路径时填原始绝对路径后再手动读取。查看保存/候选/差异，以及后端决定、配置、有序贡献、路径事件和诊断。草稿有冲突或不合法时仍可读取保存配置，但须先处理冲突才能比较候选。

**期望观察：** 未保存草稿只在内存副本中替换当前模块，不修改全局后端或其他模块。结果显示冻结的输入，编译完成、部分、过期、无效及未知分别呈现；当前文字变化不会改写旧结果身份。路径无事件不等于不存在，源路径带写透语义。跨后端赢家、外部 owner、运行集合及普通应用视图仍未验证。

**失败处理：** 草稿、解释路径或已观察上下文变化后须手动再读；返回原值不能复活旧观察。不支持、超时、输入过大和解析失败保留模块草稿，不调用普通 daemon 回退或自动重试。关闭后返回的旧响应不能进入新窗口；前一有界读取结束前不并发创建新请求。进程重建不自动重放。

**撤销：** 关闭预览只丢弃观察。未保存草稿仍可编辑或按原草稿工具处理；预览不触及配置和内核，无需清理规则。决定保存时使用原模块设置，保持保存后重启的语义；不要把预览摘要当作热应用授权。详细边界见[Manager 预览指南](sumh-module-rules.md#manager-计划预览与路径解释)。

## 20. 区分保存设置、内核状态和应用作用范围

**目的：** 检查功能为何显示关闭、未知或未就绪，并找到对应配置或诊断入口。

**适用条件：** 配套第十八批 Manager/控制器及能力快照接口。内核能力查询失败时仍须保留已保存设置，不据此删除定义。

**入口与步骤：** 挂载与隔离或独立 SUMH 配置→“能力与作用范围”→手动读取。先看各段的来源、boot ID、时间和错误，再分别核对保存值、内核 configured、active 和生效阶段；通过项目按钮进入原配置或诊断。脚本可直接运行 `/data/adb/ksud sumhp api capabilities`。完整合同见[能力中心指南](sumh-capabilities.md)。

**期望观察：** 查询不保存或应用。关闭、不支持、未知和错误有不同含义；后端能力不冒充实际挂载结果，外部 owner 未核实，原始 Release 的 KMI 推断与当前显示字符串分开。观察者说明属于代码策略，不能用 root 查询代替普通应用实测。

**失败处理：** 保留项目的旧采样与本次错误；旧 boot 的值仅作历史参考，不能与新采样拼成当前成功结论。超时或能力未知时手动重读或进入对应诊断，不自动重放，不回退到可能启动恢复的普通查询。需要绑定、完整运行集合或路径解释时进入对应详细页面。

**撤销：** 关闭查看即可。没有配置或规则需要清除；修改仍在原功能页面明确保存并按其生效阶段处理。

## 21. 分别记录普通、isolated 和 root 的合成视图

**目的：** 保存不同观察者的实际文件/目录/属性/Maps/挂载信息及身份，再与明确的检查期望比较，为设备验证提供原始证据。

**适用条件：** 专用可恢复 ARM64 Android API 31+ 测试设备、第二十三批独立 testOnly APK 和同源码 helper。当前工具不布置 SUMH 规则，独立测试 owner 与完整设备矩阵尚未完成；不能把构建或宿主合成样本当作设备通过。

**入口与步骤：** 按[观察者指南](sumh-observer-kit.md)构建测试包→明确安装→创建应用私有合成数据→导出精确请求→采集并导出普通/isolated 样本→在既有授权 root shell 用同一请求运行 helper→离线声明期望并比较。样本、请求、期望、报告和构建指纹一起保留。多进程采样不是原子快照。

**期望观察：** UID/PID/namespace/boot 直接记录或保留错误；用户输入的 config revision 始终未经独立验证。isolated 的 fresh path 拒绝与委托已打开 FD 可读是不同结果。已采集只表示拿到样本；比较器只报告声明范围的 match/mismatch/inconclusive/not_applicable。

**失败处理：** 访问拒绝、未运行、截断、混合请求/构建、namespace 变化或缺少观察者不能转成成功。超时拒绝旧回调且不自动重放；先保留错误再手动重试。隐藏缺失结论要求已成功的同观察者/探针基线和 ENOENT，EACCES 不能替代。

**撤销：** 采样不改变规则。导出证据后清除这个专用测试应用的数据；外部 helper/报告逐文件处理。工具不执行全局 clear，也不声称撤销另外手动配置的规则。

## 22. 模块重建失败后先读记录

**目的与适用条件：** 配套第二十四批控制器，在启动挂载或热启停失败、结果未知时识别已提交的计划和确认范围。需要 `module_rebuild_status:true` 及已有 root 授权。

**入口与步骤：** 精确执行 `/data/adb/ksud sumhp module rebuild-status`，保留 JSON；分别看当前 boot、latest 的阶段、最近 acknowledged 计划、intent 以及 admission，再读取运行集合和日志。该命令不启动 daemon、修改规则或触发恢复。

**期望观察：** pending 不证明未执行；partial 只确认成功调用前缀；acknowledged 不证明实际 VFS/owner/Maps 或外层命令全部成功。计划是路径描述，不固定旧 inode 或内容，内部重建 ID 与外层 operation ID 分开。

**失败处理：** 同启动未解决记录阻止重复重建；未来格式、损坏和读取错误保留文件调查，不自动重放。外层回包丢失但内层回执已完成时可独立查询证据。当前查询不是后续应用令牌。

**撤销：** 查询无需撤销；恢复配置需审查源文件与原定义，再按现有生效阶段处理，不执行留存计划或全局 clear。完整语义、容量和下一启动边界见[模块重建指南](sumh-module-rebuild.md)。

## 23. Maps 更新后分别验证旧流与新流

**目的：** 确认规则替换不会让同一条 Maps 读取流混用新旧规则，并识别仍由旧 FD 持有的内存。

**适用条件：** 包含第二十五批实现的测试内核、受现有 SUMH 策略影响的自有测试进程、专用合成文件及明确登记的受管规则。该流程是待执行的设备用例；root 的查询结果不代替普通应用读取。

**入口与步骤：** 在测试进程打开 maps/smaps 并读取一小段，保留文件对象；记录 `api inventory maps_managed` 和 `api hooks` 预算；通过已有 Maps 编辑/明确 apply 更新合成规则；继续读取旧 FD，再另行 open 并读取新 FD。同时保留进程、namespace、boot、配置与内核版本。另测先 open 但未读、首次零字节 read，以及初始空规则后再应用的情况。

**期望观察：** 已采样旧流始终使用旧规则，首次有效非零读取在更新之后的新流使用新规则；空集合也会固定。精确设备优先，同键临时规则优先。规则查询描述当前登记集合，不描述每个仍打开的旧流。VMA 本身可变化，此用例只验证规则一致性。

**失败处理：** 规则提交明确返回 `ENOMEM` 时保留旧集合，检查共享预算并关闭自有旧 FD 后明确重试；`ENOSPC` 表示临时不同键数量达到上限。丢失确认先查询，不能推断未发布。终止性读取错误后关闭并重新打开；普通用户缓冲复制 `EFAULT` 可以重试原流。读取入口观察到过滤关闭或作用范围变化时，原代理报 `EIO`，不回退原生文本；不承诺撤销已经开始的一次读取。

**撤销：** 恢复本次测试原受管定义并明确应用，关闭所有自有 FD；只在最后引用释放后期待旧代内存回收。不要用全局 clear 撤销单项测试。数量、预算、关闭和 EOF 语义见 [Maps 指南](sumh-maps-rules.md#规则快照与读取中的更新)。

**期望观察：** 输出配置 add/remove/change 与未变计数，隐藏同路径不同 ID 另报身份冲突。capture 前后双读只提供稳定性观察，不是原子快照。预览明确 can_activate=false、runtime_evaluated=false，模块/能力可应用性未评估；保存成功不等于已恢复运行状态。

**失败处理：** 版本冲突先重新查询审查；来源变化、不支持格式、损坏或不可读不当作空集合。unknown、断连或 stdout 失败先按已知 ID list/show，不自动重发写入。Manager 保留待核对记录，查询当前存在/缺失后由用户明确确认；这不证明历史操作结果。所有入口均精确本地执行，不经 daemon 或 operation 包装。

## 25. 撤销一条临时 Maps 覆盖并保留受管规则

**目的：** 清理一次数字规则实验留下的精确键，让同键受管规则按原优先级继续参与匹配。

**适用条件：** 第二十九批控制器、支持 `temporary_maps_delete` 与 `rule_inventory` 的内核、既有 root 授权；使用自有测试文件和能够确认来源的临时规则。临时集合没有每个调用者的独立 owner，token 只防止旧快照误操作，不证明该条目属于当前测试。

**入口与步骤：** 精确执行 `/data/adb/ksud sumhp sumh maps list-temporary`，按 page 的 instance_id/generation/next_cursor 读至 at_end，保留要删除项的原始数字身份和替换值。确认后执行 `sumh maps remove TARGET_INO TARGET_DEV --instance INSTANCE --generation GENERATION`；参数格式见[Maps 指南](sumh-maps-rules.md#临时数字规则的定向删除)。再次分页查询，并由受影响的自有观察者分别读取旧、新 maps FD。

**期望观察：** 成功仅删除指定临时键，其他临时及全部受管条目保留；同键受管项可能恢复优先匹配。dev 非零的删除不会退而删除 dev 0 通配。登记集合反映新状态，已固定旧流仍可保持旧规则，不能用 root 查询替代应用实测。

**失败处理：** snapshot_changed 先重新查询和审查；temporary_key_not_found 不转为全局清空；内存不足保留旧集合。未知、输出失败或断连先查询，不自动重放。旧内核不支持就保留规则并报告，不能默默用 clear 模拟。

**撤销：** 必须核对源文件当前身份后，通过已有数字 add 重新登记原单项。该直连入口不保存配置、不恢复 daemon、不记录持久 operation ID；需要追踪时可使用场景 32 的显式预约流程。两者都不会删除已保存路径定义。上述设备步骤仍待真实设备执行。

**目的：** 在界面核对临时数字规则，清理能够确认来源的单项，并识别中断后的结果不确定性。

## 27. 按故障场景读取证据并查询近期操作

**目的：** 将隐藏定义未生效、模块后端回退、受管 Maps 失败或启动保护拆成可核对的事实，避免把保存成功、历史成功或 root 查询当作当前应用视图。

**适用条件：** 第三十五批 standalone ksud、已有 root 授权；先检查 `api meta` 的 diagnostics 能力。隐藏场景需要真实稳定定义 ID，模块场景需要模块 ID；可选 operation ID 必须来自操作记录。Manager 单场景诊断包入口见场景 31，完整恢复向导仍待实现。

**入口与步骤：** 按[四场景指南](sumh-diagnostics.md)构造 schema 1 JSON，通过绝对文件或 stdin 传给 `/data/adb/ksud sumhp doctor --input`。一次选择一个场景，保存 stdout JSON 和退出码，依次检查 status、evidence、findings、next_steps 与 unchecked。需要时执行建议中的只读查询，再由自有观察者采样验证实际视图。

**期望观察：** 精确选中隐藏定义；模块仅显示当前生产 Planner 推断；Maps 对完整集合计数并标明省略行数；启动保护只解释存储门禁。saved/observed/historical/inferred 分开，近期操作只是候选关联。observed/0 表示有限证据完整，即使报告发现问题也可以返回 0。

**失败处理：** invalid 保留输入并修正；partial、stale 或 unavailable 先检查缺失来源，不能转成不支持或自动删除定义。busy/超时不自动重试，未知操作先按 ID 查询。只有只读建议携带 argv；修改建议只有说明，不拼接输入到 shell，不提供全局 clear 或“修复全部”。

**撤销：** 诊断不修改规则、配置或恢复记录，无需撤销；关闭查询也不保证整棵采样进程树立即退出。后续手动变更按对应功能指南撤销。Linux 生命周期运行、Android 采样及普通应用/isolated/root 观察者验证仍需单独执行。


## 28. 保持阅读位置并检查最新日志（当前源码已实现）

**目的：** 搜索、筛选和阅读 SUMHP 或 SUMH 内核日志，刷新后继续查看原位置，或主动跟随最新可见行。

**适用条件：** 包含第三十六批改动的 Manager，能够读取对应日志来源。界面展示一次读取快照，不能把日志内容当作当前内核状态或普通应用视图的证明。未运行设备验收，主机验证见[第三十六批记录](../../plans/SUMH-implementation-validation-batch36-2026-10-18.md)。

**入口：** Manager → SUMH → 日志。

**操作步骤：**

1. 选择守护进程或内核来源，点击刷新。系统字号较大时，来源选择和搜索框独占一行，按钮排到下一行。默认暂停跟随；同来源读取期间保留上次内容，切换来源立即清除旧来源显示。
2. 使用搜索框及更多菜单里的等级筛选。无等级筛选表示全部；无法从正式前缀识别等级的行保留在全部视图，不因正文或路径包含 `ERROR` 等单词而被误分类。
3. 阅读旧条目时保持暂停。刷新会尽量保留仍在尾部快照中的行及滚动位置；轮转或替换使原行消失时，位置会按剩余列表调整，不能恢复已丢弃的历史。
4. 打开“跟随最新日志”，在刷新或筛选完成后跳到最新可见行。滚动会暂停跟随。开关不启动自动轮询。
5. 更多菜单里的复制会复制当前筛选结果，保留原始行文字、空行和尾部空格，行分隔符统一为换行。读取或后台筛选尚未完成时，复制暂不可用。

**期望观察：** 等级从原始前缀及辅助语义表达，同时使用控制台配色；行按需显示，字体跟随系统缩放。行数是本次快照内的筛选数/总数，不是设备全部历史数量。守护进程沿用最多尾部 256 KiB、1,000 行读取，达到字节上限时丢弃首个被截断行；内核沿用最多 1 MiB 原始读取再筛选最多 1,000 条 SUMH 日志。末尾换行作为空行保留在阅读模型和复制结果中。第三十六批只改变阅读；后续第三十七批存储政策见场景 29。

**失败处理：** “刷新失败”与“没有日志”分别显示。若仍有内容，则来自上次成功读取；可以复制这些旧内容，但应附上失败信息说明快照未更新。清除筛选可恢复未分类行。实际内核查询、诊断或观察者验证按各自指南执行。

**撤销：** 关闭搜索、清除等级筛选或关闭跟随只改变阅读状态。清空日志仍需确认，仅对守护进程日志开放；它不是规则撤销或全局 clear。完整日志不写入页面恢复 Bundle，重新进入后重新读取；搜索、等级和跟随等小状态可恢复。

## 29. 核对日志保留、重复错误与清空范围（当前源码已实现）

**目的：** 识别近期日志为何被裁剪、相同错误为何汇总，以及清空后哪些信息仍保留。

**适用条件：** 第三十七批控制器提供日志政策，第四十一批 Manager 补清空文件校验；已有授权且能够访问 SUMHP 日志。内核日志和诊断包另行管理。

**入口与操作步骤：** 在 Manager 的守护进程日志页手动刷新；结合首次 Warning/Error 与 `[repeated N times]` 记录核对组件和等级。看到 storage limit 提示时按有限尾部理解当前内容；确需跨启动历史时用授权本地工具读取实际日志的 `.old`，记录版本、boot ID 和采样时间。详细预算、读取范围和失败步骤见[日志指南](sumh-log-storage.md)。

**期望观察：** 受管当前与历史路径成功维护后各不超过 1 MiB，裁剪保留最多 512 KiB 窗口中的完整记录并提示。重复汇总只在本进程精确身份上执行，32 项、30 秒窗口，无定时刷新；N 不含首次记录。背景原始 stdio 不再保存到该日志，结构化诊断仍可写入。旧打开 inode、维护失败的超大文件和外部写入不在简单路径容量保证中。

**失败处理：** 日志沉默不证明正常；空间、权限、类型、损坏 marker 或同步失败可能停止追加，后台 stderr 兜底也不持久保存。保留异常证据并查询对应运行状态，不自动重置 marker 或重放操作。分享原始日志前检查私人路径；四场景诊断可使用已有默认脱敏包并先预览。清空遇到占锁或异常文件会失败，先手动刷新、检查后再明确重试，不自动修复或重放；见[清空步骤与边界](sumh-log-storage.md#清空当前守护进程日志)。

**撤销：** 关闭筛选只改变显示；确认清空仅截断当前日志，历史、marker、配置和规则保留，已清除文字不能恢复。观察到清空后下一次同类错误重新作为首次显示。无全局 clear 步骤，也未新增可调日志容量命令。设备、多进程和断电验收仍待执行。

## 30. 留存、预览、导出和删除一份诊断包（当前源码已实现）

**目的：** 对一次故障采样保留范围明确、默认脱敏的诊断材料，先检查完整内容再决定是否导出。

**适用条件：** 第三十八批 standalone ksud、已有 root 授权及可用私有存储；检查 `api meta` 中的 `diagnostic_package_*` 能力。Manager 操作见场景 31；包内采样是 root 控制面证据，不是普通应用实测。

**入口与步骤：** 按[诊断包指南](sumh-diagnostic-packages.md)准备一个 32 位小写十六进制 ID 和四场景 schema 1 输入，执行 `doctor package create ID --input <绝对文件或->`。先保存回执，再用 `list` 和 `preview ID` 查看隐私模式、诊断状态、完整 `export_bytes`、字节数和 `package_revision`；需要导出时使用该 revision 执行 `export`，自行选择受保护的本地输出目的地。明确需要保留身份时，只在首次 create 添加 `--include-identifiers`。

**期望观察：** 默认按类型替换 boot、模块、定义、操作和 revision 等身份，包内保持关联；命令参数、路径、备注、日志和凭据不进入包。保留身份模式仍是相同受限字段集合。partial/stale/unavailable 可成功留存，saved 不等于诊断正常。预览/导出不重新采样；导出字节与预览完全一致，revision 是包括末尾换行的字节摘要。

**失败处理：** 创建回包丢失或 unknown 时先查询已知 ID，不自动重复采样。ID 已存在时不覆盖；达到 8 份或字节预算则明确拒绝，用户检查后定向删除。损坏/未来格式不自动修复或丢弃。导出失败应丢弃调用者本次不完整输出，原包继续保留；条件冲突先预览，不能忽略 revision。

**撤销：** 用已预览 revision 执行 `remove ID --revision REVISION`，随后查询该 ID；只删除本地库中指定项，不删除已导出的副本、输入文件、日志、配置或运行规则。别名只在单包内有意义，不构成保证匿名。完整 bugreport 和原 doctor 隐私行为不变；Linux/Android 运行与断电验证仍待完成。

**目的：** 从四类故障选择单场景采样，检查完整内容后保存副本，并在中断后查询已知 ID。

**适用条件：** 第三十九批 Manager 与配套打包 ksud、有效授权及私有存储。逐项能力读取成功才开放对应动作；进入页面不会自动采样。实际文件提供者、设备生命周期和 TalkBack 仍需验收。

**入口与操作步骤：** Manager → 诊断 → SUMH 诊断包，手动读取能力和列表，选择场景与所需稳定 ID。默认脱敏，保留身份须另行确认。创建后查询已登记的包 ID 并确认结果；查询到包时直接使用页面上的预览，或再次手动读取列表后选择包。展开全文，核对模式、状态和内容版本，勾选已检查后“保存副本…”。系统文件选择器返回后，应用重新按 revision 查询并比较精确内容，再写入所选位置。列表是手动快照，创建或删除后需再次读取才能更新。详见[Manager 操作指南](sumh-diagnostic-packages.md#manager-操作)。

**期望观察：** 保存成功与证据 partial/stale/unavailable 分开显示；失败保留输入，未知结果保留待查询 ID。旋转保留 Activity 内任务；进程重建保留小表单及私有检查点，不恢复报告、确认状态或变更请求。导出不会重新采样，不删除原包，也不自动分享。

**失败处理：** 检查点无法确认时不派发创建/删除；结果未知先查询指定 ID，不自动重放。能力未知或读取失败不当作空列表。导出会话丢失需重新预览；目标写入或关闭失败时检查目标位置可能存在的不完整文件，原包仍保留。

**撤销：** 取消文件选择器保留原包；删除本地包须基于当前预览单独确认，再查询 ID。已导出的副本由所选文件提供者单独管理。删除不影响日志、配置、输入文件或运行集合；不使用全局 clear。


## 32. 在脚本中追踪一次临时 Maps 精确删除（当前源码已实现）

**目的：** 删除前保留操作身份，在回包丢失后查询当次实际结果，避免将重复删除当作恢复。

**适用条件：** 第四十二批控制器、既有 root 授权以及查询/精确删除的内核能力；只操作已确认来源的临时键。此流程没有新增每调用者 owner，不代替普通应用实测。第四十三批 Manager 用法见场景 33。

**入口与步骤：** 手动完整查询 `list-temporary`，保存原值，审查精确键与 token；按[Maps 可追踪 CLI](sumh-maps-rules.md#临时删除的可追踪-cli-流程)生成规范 JSON。prepare 成功并确认 reservation_confirmed 后保存 ID，以相同文件 execute 一次；本地执行无需 daemon。之后按原 ID show/wait/result，并单独查询当前集合。

**期望观察：** started 耐久写入并读回后才提交删除，已开始/结束或不匹配预约不会再次调用。内层为 `temporary_maps_mutation`，saved/observer_verified 均为 false；历史支持与实际留存成功分开。record-only 结束不更新无关配置的核实状态，同键受管规则保持。

**失败处理：** ESTALE 重新查询并审查；开始或结束记录失败、断连、回执缺失或淘汰都先查原 ID，不自动改用新 ID 或直连重试。schema 1 回执库迁移先备份；冲突/未知格式保留原文件。旧二进制不兼容 schema 2，降级要明确转换，不能将备份直接当作当前状态。

**撤销：** 未执行预约等待自然淘汰；已删除条目须核对当前源身份后明确 add 原单项。删除历史不恢复规则，全局 clear 不作撤销。限定主机测试和 ARM64 编译证据见[第四十二批记录](../../plans/SUMH-implementation-validation-batch42-2026-10-19.md)，真实设备步骤仍待执行。

## 33. 在 Manager 追踪临时 Maps 删除并查询历史（当前源码已实现）

**目的：** 明确删除一个已审查的临时键，在页面关闭或进程重建后按操作 ID 查询该次结果。

**适用条件：** 第四十三批 Manager 与配套控制器、有效授权、可用应用私有存储及内核查询/精确删除能力。追踪不支持时可以查看规则，删除需更新控制器；能力未知时先刷新。每调用者 owner、真实设备生命周期和观察者验收仍待完成。

**入口与操作步骤：** Maps 设置→管理临时 Maps 规则→刷新规则。审查目标和替换身份、路径及来源，保存必要原值后确认删除。页面确认两次本地检查点后 execute 一次，并显示操作 ID。展开“本地删除历史”，选择该 ID 的“查询本次操作”或“最多等待 5 秒”；再单独刷新规则检查当前集合。完整合同见[Maps 工作台](sumh-maps-rules.md#manager-临时规则工作台)。

**期望观察：** 当次收到的响应与手动查询取得的回执分开；命令结束不自动等于删除成功。原始 boot、查询 boot 和历史结果分别显示。打开历史只读取本地文件，不自动查询内核或重放；旋转和关闭重开不重放操作，同一 Activity 保留已观察列表、选择和结果；只有进程重建不恢复删除队列、规则列表或 token。删除后旧列表仍需单独刷新。成功回执只证明当时内核确认，不证明当前应用视图。

**失败处理：** 检查点不确定时不 execute；execute 后结果不明先查询原 ID，不重新预约或回退直连。回执未留存、操作未结束、历史淘汰或跨启动均保留对应含义，不能从条目缺失补造成功。记录满额不自动丢弃未知操作；未来/损坏格式不覆盖。保存错误可能留下旧或新检查点，需重新读取并核对，不能清空重置后重试删除。

**撤销：** “忘记本地记录”另行确认，仅移除本机关联，不取消服务端操作、不删服务端历史、不恢复规则。需要以后查询先复制 ID。删除规则的撤销仍需核对当前身份后明确添加原单项；没有全局 clear 步骤。主机与构建验证见[第四十三批记录](../../plans/SUMH-implementation-validation-batch43-2026-10-19.md)，设备验证独立保留。
