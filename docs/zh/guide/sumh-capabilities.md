# SUMH 能力与作用范围中心

本页说明第十八批新增的只读能力中心。它把保存设置、内核控制状态、构建字符串及后端能力放在同一页面，但这些项目是分别采样的，不能作为普通应用实测或全部规则已生效的证明。详细集合检查继续使用[运行状态与规则查询](sumh-runtime-state.md)、[模块计划预览](sumh-module-rules.md)和[Maps 预览](sumh-maps-rules.md)。

## 打开与读取

在 Manager 的“挂载与隔离”或独立 SUMH 配置页面打开“能力与作用范围”，再点击读取。打开页面、旋转、返回前台不会自动读取。读取时旧结果标记为过期；失败后保留此前可用的项目及其原始 boot ID、采样时间和来源，同时显示本次错误。没有旧结果的项目保持未知。

读取不修改设置、规则、恢复状态或编辑器草稿。页面里的配置与诊断按钮进入已有工作流，具体保存、应用与重启仍按原工作流执行。离开页面后旧请求的迟到结果不会进入重新打开的会话；上一请求返回前不能再启动同一页面的新读取。进程重建后需要手动重新读取。

授权 root shell 可直接使用：

```sh
/data/adb/ksud sumhp api capabilities
```

这是精确本地只读入口，不启动 daemon，不自动恢复，不创建配置、日志或迁移备份。不要添加全局包装选项或通过 `daemon call` 转发。Manager 使用专用有界传输；内部 `--channel` 不是公开脚本参数。旧的通用综合查询仍保留原有行为，不能把本接口的无恢复保证推广到所有旧命令。

## 怎样解读结果

| 信息 | 可确认的事实 | 不能据此确认 |
| --- | --- | --- |
| 功能支持 | 本次能力或结构化运行查询返回的支持情况 | 查询失败不等于不支持，支持不等于打开 |
| 保存设置 | 配置文件中解析出的意图及该文件 revision | 已应用到内核，或全部配置的统一版本 |
| 内核 configured | 采样时实际控制开关 | 配置文件值，或功能已对某个应用生效 |
| 内核 active | 采样时机制的就绪状态 | 普通应用文件、Maps 或挂载视图已验证 |
| 后端能力 | SUMH 协议结果、OverlayFS 注册情况、Magic 策略编入控制器 | 挂载成功、模块实际赢家或本次启动 owner |
| 构建原值与当前值 | 初始 UTS 中读取的字符串以及内核保留的原始值 | 已克隆 UTS 命名空间全部同步，或 ABI 兼容 |

原始 Release 推导的 KMI **只是标签推断**，与当前显示字符串分开展示；它不是 ABI 探测，也不应单独用于选择内核镜像。Kernel Build 的实际修改方法和生效阶段见[构建字符串指南](sumh-kernel-build.md)。

保存值、内核开关和 active 分别展示。即使保存值与开关相同，也不生成 applied revision 或“全部已应用”的结论。后端可用性与实际运行后端分别展示；外部 owner 本批尚未可靠收集，保持未知，不把旧查询返回的空字符串解释成“没有冲突”。

## 按观察者理解作用范围

以下是对仓库内核策略的说明，不是对连接设备中任意进程的现场检测。共享 UID、工作资料、isolated service、命名空间、已打开 FD 和之后的新 open 都可能需要分别验证。

| 功能 | 策略依据与验证方法 |
| --- | --- |
| 模块文件视图 | 根据应用卸载策略选择 VIEW/SPOOF；isolated/app-zygote UID 使用 SPOOF，非应用 UID 通常使用 VIEW。root 读取不能代替目标应用验证。 |
| 用户隐藏 | root、已授权应用、当前解析进程等有豁免；存储服务在受管存储父目录还有专门处理。规则登记、绑定成功和目标应用确实看不见是不同证据。 |
| 挂载信息与 statfs | 使用独立的挂载观察者策略，普通未授权应用和 isolated 进程是目标；statfs 还依赖挂载隐藏已配置且机制可用。不能用模块文件是否可见来推断挂载信息。 |
| Overlay xattr | 对已标记文件系统使用挂载观察者策略过滤相应属性；保存开关不能证明当前标记集合完整。 |
| Stealth | 对 SPOOF 范围的 `/dev` 目录枚举进行专门过滤，不等同于用户隐藏规则。 |
| Maps | 显式路径/身份规则依照 SPOOF 策略及开关工作；它修改输出表示，不替换被映射文件内容。文件身份变化后使用已有预览与明确重新应用。 |
| Kernel Build | 改变初始 UTS 字符串，不是按应用切换的规则；原来克隆的 UTS 命名空间不保证同步。 |
| 自定义 su 路径 | 使用独立授权可见性，不能从模块或用户隐藏状态推断。操作仍通过既有 su 设置。 |

中心始终注明未收集应用实测。验证步骤见[SUMH 行为验证](sumh-validation.md)；专用合成 APK、isolated service 和 root helper 的自动验证包仍属于 F13 待实现范围。

## JSON 合同与失败处理

`api meta` 中逐项宣告 `capability_snapshot_schema:1`、`capability_snapshot_read_only:true`、`capability_snapshot_transport_schema:1` 和响应预算；这些是控制器能力，不能仅凭协议号推断内核支持。Manager 协商失败时不会退回普通 daemon 查询。

响应 `resource=capability_snapshot`、`observation=control_plane_only`、`atomic=false`。`sections` 含 `saved`、`runtime`、`build`、`backends` 和 `owner`；每项都有 status、reason、errno、source 和单调时钟开始/结束时间。单调毫秒不是墙上日期，只在对应 boot 身份下解释。未知、明确不支持和读取错误分别保留；不能把 `value:null` 读作关闭。

运行段复用 `api runtime` 的结构，保留独立的 boot ID、instance、generation、协议和能力信息。generation 仅跟踪其合同中的控制变更，不代表文件内容、事件绑定或所有资源的版本。构建段注明是否经过控制 generation 前后核对；这也不能排除第三方直接修改 UTS。

配置读取有 256 KiB 预算，超过预算保留磁盘文件并显示不可读，不截断后使用默认值。配置在本段采样前后读取，文件改变时不把结果当作稳定保存值。整个查询前后 boot ID 缺失或变化时返回未知。原始响应最多 64 KiB，沿用独立传输的 8 秒等待、JNI 调用者 10 秒等待及内部只读工作进程 5 秒预算，不扩大普通 IPC。内核/策略不支持 pidfd、命名空间操作失败或槽位仍被前次工作占用时，结果可能未知；不自动重试。

失败时先保留错误和旧采样身份，再手动刷新或进入对应配置/诊断。旧 boot 的保留结果只能作为历史观察，不能与新 boot 的设置拼成当前成功证明。需要完整定义、规则、操作历史或模块路径解释时进入对应页面；本中心不扫描全量模块和 Maps/HIDE 路径。

**撤销：** 关闭页面即可结束查看，没有需要撤销的配置。关闭不承诺底层读取已经立即取消，但迟到结果与新的页面会话隔离。不得使用全局 clear 作为读取失败的处理方法。
